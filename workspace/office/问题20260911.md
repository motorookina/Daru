# 问题记录：数据族概念重定义（字段驱动版）

> 日期：2026-09-11
> 相关文件：`pg-ops-agent-v1.2/backend/app/routers/agent_compute.py`（及 `agent_invoke.py` 的标的解析）
> 结论状态：核心目标已锁定为**字段驱动**，方案收敛为「字段词汇表 + 数据集注册表（family × asset）+ 标的分类器」。

---

## 一、核心目标（先对齐，再谈重设计）

本服务（`/v1/agent/compute` 结构化取数口）的取数单元是**三元组**：

| 谁 | 哪天 | 要什么 |
| --- | --- | --- |
| `target`（标的） | `as_of`（分析时点） | `fields`（字段清单） |

对应代码 [agent_compute.py:700-711](pg-ops-agent-v1.2/backend/app/routers/agent_compute.py#L700-L711)：先解析 `target`，再取 `fields`（不给则落 `DEFAULT_FIELDS` 8 个默认字段）。

**模型定性：字段驱动（field-list driven）**，即调用方给字段清单，系统按「数据族」组织取数。**不是**「标的全景」（只给 target+as_of 就自动取回该标的所有已登记字段）——需求报告 [报告_动态获取_金融数据服务智能体.md:13](报告_动态获取_金融数据服务智能体.md#L13) 明确要求「避免一次请求全量导出式的低效取数」。

一次请求可以**跨多个数据族同时取数**（如行情 + 估值 + 财务），但这是「给定字段清单的前提下跨族」，不是「不指定就取全部」。

---

## 二、问题描述（为什么要改）

现有 `Q, B, F, S, I = "quote", "basic", "fina", "stock", "index"` 这一分类不合理，两个具体问题：

1. **分类维度混乱**：`Q(行情) / B(估值规模) / F(财务)` 是「数据口径 / 时点语义」维度；而 `S(股票基础) / I(指数)` 是「资产类型」维度。两类**正交**的东西被硬塞进一个平铺枚举里，语义互相污染。
2. **以字段为基准不健壮**：当前 `FIELD_DICT` 是 `字段 → 唯一(api, col)` 的 1:1 硬编码。随着扩展表增加，会出现「很多表对应同一个字段」——例如 `close` 同时存在于股票日线 `daily` 和指数日线 `index_daily`，`pe_ttm` 同时存在于 `daily_basic` 和 `index_dailybasic`。1:1 映射无法表达。

---

## 三、现状诊断

### 1. `FIELD_DICT[f]["cat"]` 是死代码
字段字典每一行都挂了 `cat`（`Q/B/F/S/I`，见 [agent_compute.py:110-170](pg-ops-agent-v1.2/backend/app/routers/agent_compute.py#L110-L170)），但全仓库 `.py` 中没有任何地方读取 `["cat"]` 或 `.get("cat")`。它只是「注释」，不是真正起作用的分类。

### 2. 真正驱动行为的族是 `_api_family(api)`
[agent_compute.py:398-403](pg-ops-agent-v1.2/backend/app/routers/agent_compute.py#L398-L403) 返回 `quote_daily / financial_statement / static_reference / unregistered` 四类，才是：
- `_collect` 的三时点标注（observed_at / available_at）依据；
- `_freshness` 的新鲜度策略依据；
- PIT 判定依据。

而它是靠 `_DAILY_APIS / _FINA_APIS / STATIC_ONLY_APIS` 三个**硬编码集合**判断的，与字段上的 `cat` 完全脱节。

### 3. 结论
代码里**并存两套「数据族」**：字段上挂的语义族（没人用）+ API 集合层的行为族（有人用），两套各说各话，是「不清晰」的根本原因。

补充观察：`_DAILY_APIS` 里已躺了 `index_daily / index_dailybasic / idx_factor_pro`，但 `FIELD_DICT` 没有任何字段指向它们——「资产类型分表」的苗头早已出现，只是没接上线（`I` 族是空壳）。

---

## 四、重新定义方案（字段驱动版）

### 4.1 核心思路：三个维度各归其位

在字段驱动模型下，「数据族」最终只指 **`family`（时点语义）**，它是挂在**数据集**上的一个标签。三个维度各自有固定来源，谁都不该写进字段字典：

| 维度 | 是什么 | 谁来提供 | 写在哪 |
| --- | --- | --- | --- |
| **field** | 语义概念（选什么数） | 调用方 | `FIELD_DICT`（词汇表） |
| **asset** | 资产类型（去哪张物理表） | **由 target 推出** | 标的分类器 `classify_asset` |
| **family** | 时点语义（时间怎么取） | **从命中表读回** | `DATASET`（数据集注册表） |

**关键洞察**：字段字典之所以可以（也应当）保持零维度，是因为另外两维天生不属于字段——
- `asset` 不是字段的属性：`pe_ttm` 同时适用于股票和指数，它不知道自己属于哪类资产；
- `family` 也不是字段的属性：它是「这行数据在时间轴上怎么长出来」的物理表属性，字段名锚到某张表上才有资格谈时点。

### 4.2 字段字典：退化成纯词汇表

```python
# 只声明「语义名 + 单位」，不再有 api / col / cat
FIELD_DICT = {
    "close":    {"unit": "元"},
    "pct_chg":  {"unit": "%"},
    "pe_ttm":   {"unit": "倍"},
    "pb":       {"unit": "倍"},
    "n_income": {"unit": "元"},
    "roe":      {"unit": "%"},
    "name":     {"unit": ""},
    "industry": {"unit": ""},
}
```

以后要支持同义词（「市盈率」「PE(TTM)」→ `pe_ttm`），单独建一张别名表，别混进字段字典。

### 4.3 数据集注册表：family × asset 两轴 + 物理列

把散落三处（`DATASET_HISTORICAL` / `_DAILY_APIS` / `_FINA_APIS`）的东西收敛进一张注册表，每张表自证其「时点语义 + 资产类型 + 有无历史 + 提供哪些列」：

```python
DATASET = {
    # 日频行情（family=daily）：股票走 daily，指数走 index_daily
    "daily":            {"family": "daily",  "asset": "stock", "historical": True,  "cols": {"close": "close", "open": "open", "pct_chg": "pct_chg"}},
    "index_daily":      {"family": "daily",  "asset": "index", "historical": True,  "cols": {"close": "close", "pct_chg": "pct_chg"}},
    # 日频估值（family=daily）
    "daily_basic":      {"family": "daily",  "asset": "stock", "historical": True,  "cols": {"pe_ttm": "pe_ttm", "pb": "pb", "total_mv": "total_mv"}},
    "index_dailybasic": {"family": "daily",  "asset": "index", "historical": True,  "cols": {"pe_ttm": "pe_ttm", "pb": "pb"}},
    # 财务（family=period）：按报告期 + 公告日门控
    "income":           {"family": "period", "asset": "stock", "historical": True,  "cols": {"n_income": "n_income", "revenue": "revenue"}},
    "fina_indicator":   {"family": "period", "asset": "stock", "historical": True,  "cols": {"roe": "roe", "eps": "eps"}},
    # 静态快照（family=static）：无历史版本
    "stock_basic":      {"family": "static", "asset": "stock", "historical": False, "cols": {"name": "name", "industry": "industry"}},
    "index_basic":      {"family": "static", "asset": "index", "historical": False, "cols": {"name": "name"}},
}
```

说明：
- **`family` 决定「时间语义」**：`daily`（交易日粒度，观测日=可见日=交易日）、`period`（观测日=报告期 end_date，可见日=公告日 ann_date）、`static`（无时点）。
- **`asset` 决定「物理表」**：股票 vs 指数分表。
- **`historical` 决定「PIT 能力」**：是否有历史版本/分区。`static` 表天然 `historical=False`；`daily`/`period` 表若按日/报告期分区则为 `True`（与现有 `DATASET_HISTORICAL` 语义一致，但并入注册表统一管理）。

### 4.4 解析流水线

```
target  ──► _resolve_target ──► ts_code ──► classify_asset ──► asset_class (stock/index/...)
fields  ──► FIELD_DICT ──► 语义名 + unit（只做词汇查询）

对每个 field： resolve(field, asset_class)
    = 在 DATASET 里找 { asset == asset_class 且 field ∈ cols } 的表
    → 命中后读该表的 family + historical
    → family 决定 observed_at/available_at/PIT/freshness 的标注方式
    → 走对应取数通道（daily 类 / period 类 / static 类）
```

```python
def resolve(field: str, asset_class: str) -> list[str]:
    """返回候选表名列表。消歧不了就返回全部候选，让路由层定（不擅自挑）。"""
    return [api for api, m in DATASET.items()
            if m["asset"] == asset_class and field in m["cols"]]
```

`family` 在 resolve **之后**才被读出来用——它不参与「选表」，只参与「选表之后怎么标时点、怎么判新鲜度」。这正是现在 `_api_family` 想干的事，只不过从三个硬编码集合收敛进一张注册表。

## 五、例子说明

### 例子 1：同一个字段、不同标的 → 路由到不同表

都查 `close` 和 `pe_ttm`，但 target 不同：

| target | asset | `close` → | `pe_ttm` → |
| --- | --- | --- | --- |
| `600519.SH`（贵州茅台，股票） | stock | `daily` | `daily_basic` |
| `000300.SH`（沪深300，指数） | index | `index_daily` | `index_dailybasic` |

`resolve("close", "stock")` 命中 `daily`；`resolve("close", "index")` 命中 `index_daily`。用户担心的「很多表对应同一个字段」，就靠 `asset` 这一维在 resolve 时消歧了——**不需要为指数再造 `close_index` 之类的字段名**。

### 例子 2：一次请求跨三个族（完整走一遍）

请求：
```json
{
  "target": "600519.SH",
  "as_of": "20250630",
  "fields": ["close", "pe_ttm", "n_income", "name"]
}
```

解析：

| field | asset | 命中表 | family | historical |
| --- | --- | --- | --- | --- |
| `close` | stock | `daily` | daily | True |
| `pe_ttm` | stock | `daily_basic` | daily | True |
| `n_income` | stock | `income` | period | True |
| `name` | stock | `stock_basic` | static | False |

随后按 family 各自标注时点（对应现有 `_collect` 逻辑）：

- **daily 族**（close / pe_ttm）：向前吸附到 `as_of=20250630` 或之前最近一个交易日；`observed_at = available_at = 交易日`。
- **period 族**（n_income）：只取 `ann_date ≤ 20250630` 的最新一份财报；`observed_at = 报告期 end_date`，`available_at = 公告日 ann_date`。
- **static 族**（name）：无时点；若 `as_of` 是历史请求（超过 30 天容差），该字段被**扣留**（`pit_withheld`），不得用今天的值冒充当时的值。

PIT 判定 = 命中表全部「来源是数据库 且 `historical=True`」。本例中若 name 来自 `stock_basic`（historical=False），则整体 `point_in_time=false`，并在 `pit_detail` 里标出是哪个表拖累的。

### 例子 3：asset 消歧不了怎么办

若 `classify_asset(ts_code)` 无法确定资产类型（既不在 `stock_basic` 也不在 `index_basic`），不硬挑，返回 `asset="unknown"`。此时 `resolve` 可能返回**多张候选表**（如 `close` 同时命中 `daily` 和 `index_daily`），就把 candidates 交回路由层决定——与 `_resolve_target` 的「歧义不擅自挑」哲学一致。

```python
    # 简单版：按代码前缀/后缀规则（.SH/.SZ/.BJ + 6 位编码段）粗判
```

两个都查不到 → `unknown`，让路由层决定（同上哲学）。

## 七、落地路径（渐进式）

1. **第一步（低风险）**：删掉 `cat`（或明确降级为文档注释）；把 `_api_family` 从「硬编码集合判断」改成「读 DATASET 注册表」，成为唯一权威的族定义。
2. **第二步**：`FIELD_DICT` 去 `api`/`col`/`cat`，物理列映射移入 `DATASET` 注册表；字段只留 unit。同步把 `DATASET_HISTORICAL` 并进注册表。
3. **第三步**：引入 `classify_asset`，`resolve(field, asset_class)` 支持股票 / 指数分表，补齐 index 族字段（现在 `I` 是空壳）。

关键点：`_collect` 和 `_freshness` 现在已按 `_api_family`（而非表名）做分支，迁移成本低——只需把「表 → 族」映射从三个集合改成一个注册表，再给字段解析加一层 asset 消歧。

---

## 八、一句话总结

**字段驱动下，「数据族」只指 `family`（时点语义），它是挂在数据集上的一个标签；`asset`（资产类型）是另一个正交标签，同样挂在数据集上、由 target 决定；字段字典退化成纯词汇表。三者各归其位后，Q/B/F/S/I 的混维、字段 1:1 硬编码、以及「到底几个维度」的困惑全部消解。**
